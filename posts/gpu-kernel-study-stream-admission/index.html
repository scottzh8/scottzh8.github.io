Learning notes · GPU kernels · Study 1 · Nov 2026

Question: two kernels on two CUDA streams share one GPU. When does the second one get SMs?
Hardware: one NVIDIA B200, 148 SMs, compute capability 10.0 (sm_100)
Tools: CUDA C++ (nvcc), PyTorch streams and profiler, %globaltimer/%smid per-block stamps, Perfetto; a Triton companion run
Status: study notes. Each configuration has one profiled run (the timelines below) plus 20 unprofiled repeats per launch order (the medians). Observed behavior on this device, not a guarantee about every CUDA device.

TL;DR

  • A stream is an ordering promise, not a reservation. Work in one stream runs in order; two streams promise nothing about each other, and neither owns any SMs.
  • A thread block lands on an SM only when the whole block fits (threads, registers, shared memory, block slots). Once there, it stays on that SM until it exits.
  • A cooperative grid was admitted all at once. With 144 cooperative blocks waiting and only 52 free SMs, nothing started. The grid started (all 144 blocks within 0.6 µs) as soon as 144 SMs were free: at 3.1 ms with four long-running B blocks, at 4.6 ms with five.
  • An ordinary launch of the same grid started in about 17 µs on the 52 free SMs and ran in waves.
  • The 1 ms “grid sync” slices were waiting, not barrier cost. One block arrived 1 ms late; the release took about 0.13 µs across all 144 SMs.
  • A grid barrier keeps finished blocks on their SMs. With A launched first, the barrier made B’s regular blocks finish about 1 ms later.

Part 1: from launch to an SM#

Before the experiment, here is the path a kernel launch takes, from the top. The CUDA programming model is documented, and so are the occupancy limits. The hardware scheduler below the driver largely isn’t, so when I describe it I say where the description comes from.

What a stream actually promises#

A CUDA stream is a queue of work with one rule: operations in the same stream run in the order they were issued, and each finishes before the next starts. Operations in different streams have no ordering between them unless you add one (events, cudaStreamWaitEvent, a synchronize). That is the whole contract. A stream doesn’t own SMs, doesn’t reserve memory bandwidth and has no priority unless you create it with one.

In PyTorch the same idea looks like this. It is the shape of the harness used below:

s_a, s_b = torch.cuda.Stream(), torch.cuda.Stream()

with torch.cuda.stream(s_b):
    launch_b()          # returns as soon as the launch is queued
with torch.cuda.stream(s_a):
    launch_a()          # also returns immediately; no wait between the two
torch.cuda.synchronize()  # the host blocks here, once, until both are done

Kernel launches are asynchronous. The host call returns when the launch is queued, not when the kernel starts. In the profiled runs below, cudaLaunchCooperativeKernel returned in about 6 µs, even in the run where the GPU didn’t start that kernel for another 3.1 ms. The host-side trace shows none of the waiting.

What the driver does with a launch#

Below cudaLaunchKernel there are a few layers. This is how NVIDIA’s open-source kernel driver and its published hardware headers describe them. The exact details vary by GPU generation.

  • Channel. A channel is the GPU’s unit of command submission: an independent command queue belonging to one context. The driver creates channels for a context and maps streams onto them.
  • Pushbuffer. A launch becomes a short sequence of commands (“methods”) written into a buffer in memory. For a compute launch, the core of it is a descriptor of the grid: grid and block dimensions, shared memory size, register count, kernel entry point and parameters. NVIDIA’s open headers call this descriptor a QMD.
  • GPFIFO and doorbell. The driver appends a pointer to the new pushbuffer segment to the channel’s GPFIFO, a ring buffer of such pointers. It then writes a doorbell register to tell the GPU there’s new work. On current GPUs this happens from user space, with no system call per launch.
  • Host interface. The GPU fetches GPFIFO entries, reads the pushbuffer, decodes the methods and forwards compute work to the compute engine’s front end.

Streams, connections and Hyper-Q#

How many independent queues does the GPU see? Since Kepler, NVIDIA GPUs have had several hardware-managed queues (“Hyper-Q”; the GK110 whitepaper says 32). The CUDA driver multiplexes your streams onto a pool of them. The size of that pool is documented as an environment variable: CUDA_DEVICE_MAX_CONNECTIONS (default 8, up to 32). If you have more busy streams than connections, two unrelated streams can end up in one hardware queue and serialize behind each other even though the API says they’re independent. This experiment uses only two streams, so it never comes close.

Admission: when does a block get an SM?#

The GPU doesn’t schedule a kernel onto SMs. It schedules thread blocks (CTAs). The Kepler whitepaper names a Grid Management Unit and a CUDA Work Distributor for this job. Current generations don’t publish an equivalent block diagram, so I’ll call it “the work distributor” and describe only what’s documented or measured:

  1. Pending grids, possibly from several streams, wait in the front end.
  2. The distributor takes the next block of a runnable grid and looks for an SM where the whole block fits in what is still free.
  3. The block is placed. It stays on that SM, holding its resources, until every thread in it exits. Blocks don’t migrate and don’t get partially admitted. (Compute preemption, which saves and restores a whole context when the GPU time-slices between processes, is the exception; it doesn’t come up here.)
  4. When a block exits, its resources free up and the next block (from any eligible grid) can use them.

“Fits” means every per-SM limit at once. These are the limits for this B200. The first four come straight from the device properties in the profiler trace:

Per-SM resource (cc 10.0)LimitUsed per block in this study
Threads2,04832 (one warp)
Registers65,53616 / thread → 512
Shared memory233,472 B (228 KiB)B: 232,448 B · A: 229,316 B
Max shared memory one block may opt into232,448 B (227 KiB)(B asks for exactly this)

So the shared-memory request is what decides admission. The CUDA programming guide also says the system reserves 1 KiB of shared memory per resident block on recent GPUs. With that included, a B block needs 232,448 + 1,024 = 233,472 B, exactly one whole SM. An A block needs 230,340 B, so two of anything don’t fit on one SM. Each SM can hold one block from either kernel, never two. The 148 SMs become 148 slots, which makes the arithmetic of the experiment visible.

That’s a deliberate setup, not the normal case. A small block with no shared-memory request uses a sliver of each limit, so many blocks, from different kernels, can share one SM. The Triton companion run at the end shows exactly that.

Admission order (which block goes to which SM, and which of two runnable grids wins a free SM) is not specified by CUDA. The SM numbers in the timelines below are just what happened here.

Cooperative launches#

cooperative_groups::this_grid().sync() is a barrier across every block of a grid. It can only work if all blocks are resident at the same time: a block that has not been admitted can’t arrive, and blocks spinning at the barrier would never exit to make room for it. CUDA therefore requires grid-wide sync to be launched with cudaLaunchCooperativeKernel. That call rejects grids larger than what the device can hold at once (cudaErrorCooperativeLaunchTooLarge), computed from the occupancy calculator. Here that’s 1 block/SM × 148 SMs = 148 ≥ 144, so the launch is legal.

The documentation guarantees co-residency, but it doesn’t say how the guarantee is met when another stream is already occupying SMs. A legal 144-block cooperative grid could arrive while only 52 SMs are free. That’s the question the experiment asks.

Part 2: the experiment#

Setup#

Two kernels, two streams, one GPU, and nothing else on it (checked with nvidia-smi first):

  • B: 96 ordinary blocks on its own stream. Every B block spins for 3 ms, then a 0.1 ms tail. Blocks 0–3 are stragglers: they spin 3 ms longer (6 ms total). In the five-straggler variant, block 4 spins 1.5 ms longer (4.5 ms).
  • A: 144 blocks on another stream, launched cooperatively in the main arms. Every A block spins for 2 ms; block 0 spins 3 ms (a deliberate late arrival). Then comes an optional this_grid().sync(), then a 0.1 ms tail, except block 1, whose tail is 0.6 ms.
  • One block per SM for both kernels, forced by the shared-memory sizes above.
  • Submission order: B then A (“B first”) or A then B, with no wait between the two launches.

Three configurations of A, each run with four and five stragglers and in both launch orders:

ArmA launchGrid barrier in A
coop1-sync1cooperativeyes
coop1-sync0cooperativeno
coop0-sync0ordinary cudaLaunchKernelno (an ordinary launch can’t use one)

The cooperative-without-barrier arm separates the two choices. It shows whether the launch mode alone changes admission, or whether the barrier does.

What should happen#

Count SMs with B submitted first. At t ≈ 0, B’s 96 blocks take 96 SMs and 52 are free. A needs 144.

  • Hypothesis 1: all-or-nothing admission. To keep its co-residency promise, a cooperative grid starts only when all of its blocks can be placed. The regular B blocks end at 3 ms + 0.1 ms ≈ 3.1 ms. That leaves 4 stragglers, so 148 − 4 = 144 free, exactly enough. Prediction: A starts at ≈ 3.1 ms, every block at nearly the same moment, on every SM except the four straggler SMs. With five stragglers, 148 − 5 = 143 < 144, so A must wait for the fifth one to end at 4.5 + 0.1 ≈ 4.6 ms.
  • Hypothesis 2: incremental admission. Cooperative blocks are placed as SMs free up, like ordinary ones. Prediction: A starts within tens of µs on the 52 free SMs, the rest trickle in, and the barrier simply waits longer. In this particular setup that wouldn’t even deadlock, because B eventually finishes. In general it could, which is why I expected Hypothesis 1.
  • Control: ordinary A. No co-residency promise, so A should start almost immediately on the 52 free SMs and run in waves: 52 blocks, then more as A’s own 2 ms blocks finish, then the rest when B’s regular blocks free 92 SMs at 3.1 ms.

The kernel and how it’s instrumented#

The whole kernel is a timed spin with an optional barrier. What matters is where it records time. One compiled kernel serves as both A and B: the delay argument tells it which one it is. The captured source packs every per-block duration into a single nested ternary. Below, those durations are pulled out into two small helpers with the same values, and comments are added; the rest is the captured source, lightly reformatted:

#include <cooperative_groups.h>

constexpr unsigned long long US = 1000, MS = 1000 * US;   // %globaltimer counts nanoseconds

__device__ unsigned long long timer() {           // GPU-wide nanosecond clock
  unsigned long long v;
  asm volatile("mov.u64 %0, %%globaltimer;" : "=l"(v));
  return v;
}

// How long a block spins before the (optional) barrier.
// B is launched with delay = -4 or -5 (that many stragglers); A with delay = 2 ms.
__device__ unsigned long long work_ns(int block, int delay) {
  bool is_b = delay < 0;
  if (is_b) {
    int stragglers = -delay;
    if (block < 4)                       return 6 * MS;        // stragglers 0-3
    if (stragglers == 5 && block == 4)   return 4 * MS + 500 * US;  // 5th straggler
    return 3 * MS;                                             // regular B block
  }
  if (block == 0) return delay + 1 * MS;   // A block 0 reaches the barrier 1 ms late
  return delay;                            // every other A block: 2 ms
}

// How long a block spins after the barrier.
__device__ unsigned long long tail_ns(int block, int delay) {
  bool is_a = delay >= 0;
  if (is_a && block == 1) return 600 * US; // A block 1: long tail
  return 100 * US;                         // everyone else
}

extern "C" __global__ void toy(unsigned long long *out, int barrier, int delay) {
  int block = blockIdx.x;
  unsigned sm;
  asm volatile("mov.u32 %0, %%smid;" : "=r"(sm));  // which SM this block landed on

  auto start = timer();
  while (timer() - start < work_ns(block, delay)) {}       // "work"
  auto arrival = timer();
  if (barrier) cooperative_groups::this_grid().sync();     // A only
  auto passed = timer();
  while (timer() - passed < tail_ns(block, delay)) {}      // "tail"

  if (threadIdx.x == 0) {                    // one row per block: [sm, t0, t1, t2, t3]
    out += 5 * block;
    out[0] = sm; out[1] = start; out[2] = arrival; out[3] = passed; out[4] = timer();
  }
}

The launcher picks ordinary or cooperative launch and passes the stream handle from PyTorch:

extern "C" int launch(void *out, int count, int barrier, int coop, int delay,
                      int smem, void *stream) {
  void *args[] = {&out, &barrier, &delay};
  // allow up to 227 KiB of dynamic shared memory per block
  cudaFuncSetAttribute(toy, cudaFuncAttributeMaxDynamicSharedMemorySize, 232448);
  if (coop)
    return cudaLaunchCooperativeKernel((void *)toy, dim3(count), dim3(32), args,
                                       smem, (cudaStream_t)stream);
  return cudaLaunchKernel((void *)toy, dim3(count), dim3(32), args, smem,
                          (cudaStream_t)stream);
}

It’s compiled with nvcc -arch=sm_100 -rdc=true -shared (grid sync needs relocatable device code) and loaded with ctypes. A runs with 229,316 B of dynamic shared memory per block and B with 232,448 B. The Python side does a warm-up of each launch, then one profiled iteration:

with torch.profiler.profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA]) as prof:
    for i in ((1, 0) if b_first else (0, 1)):   # submit both, no wait in between
        launch(i)                                # each on its own torch.cuda.Stream
    torch.cuda.synchronize()
prof.export_chrome_trace(name + ".json")             # kernel-level view (one slice per kernel)
torch.save([t.cpu() for t in out], name + ".pt")     # block-level stamps, same iteration

Then 20 unprofiled trials per launch order, alternating the order between trials to reduce order bias. The trials record summary numbers such as “first A start − first B start” and “B blocks still running when A started”.

What the stamps do and don’t mean. %globaltimer is a GPU-wide clock (it advanced in 32 ns steps here), so stamps from different SMs are comparable. A block’s start is when its first instruction ran, not when the hardware decided to admit it. Likewise end is a stamp just before exit. Each “block” bar below is therefore an instrumented interval, slightly inside the true residency. Only thread 0 writes, so each block produces exactly one row.

From stamps to a timeline. A short script turns each [blocks, 5] tensor into a Chrome trace that Perfetto can open: one lane per block with three slices (work, sync or gap, tail), plus a live-block counter (+1 at each start, −1 at each end). Times are relative to the earliest block start:

for block, (sm, start, arrival, passed, end) in enumerate(rows):
    lane = dict(pid=kernel_id, tid=block + 1)
    for phase, l, r in [("work", start, arrival),
                        ("grid sync" if barrier else "no barrier", arrival, passed),
                        ("tail", passed, end)]:
        events.append(dict(**lane, ph="X", name=phase, ts=(l - origin) / 1000,
                           dur=(r - l) / 1000, args={"SM": sm, "block": block}))

Walking through the traces#

The kernel-level view hides the reason#

The PyTorch trace has one slice per kernel. For the four-straggler, barrier, B-first run (times relative to the first runtime call; the first cudaFuncSetAttribute took about 1.6 ms, a one-time cost):

EventStarts atDuration
cudaLaunchKernel (B)1,599.3 µs19.0 µs
cudaLaunchCooperativeKernel (A)1,662.3 µs6.2 µs
B kernel on GPU (96 blocks, stream 17)1,618.3 µs6,101.7 µs
A kernel on GPU (144 blocks, stream 13)4,719.3 µs3,602.3 µs

A was submitted 44 µs after B started, and the host call returned in 6 µs. The A kernel slice starts 3.1 ms later. From this view alone you could guess “the streams serialized” or “the driver delayed the launch”. The block-level view shows what actually held it up.

Four stragglers: A waits for exactly 144 free SMs#

In this profiled run:

  • B’s 96 blocks landed on SMs 0–89 and 142–147. SMs 90–141 (52 of them) were idle for 3.1 ms while a 144-block grid was waiting.
  • The 92 regular B blocks ended at ≈ 3.10 ms. The first A block started at 3,101.0 µs, and all 144 had started within 0.6 µs of each other.
  • At that moment exactly 4 B blocks were still running, on SMs 142–145. A ran on all 148 SMs except those four.

The 20 repeated trials agree. Every B-first median shows A starting 3.1 ms after B with 4 B blocks still live, with or without the grid barrier:

B submitted first (median of 20)First A start after first B start, 4 / 5 stragglersB blocks still live at first A start, 4 / 5
Cooperative A, grid sync3.101 / 4.600 ms4 / 4
Cooperative A, no grid sync3.101 / 4.600 ms4 / 4
Ordinary A0.017 / 0.016 ms96 / 96

Hypothesis 1 holds, and the barrier doesn’t matter for admission. The cooperative launch is what makes A wait. A cooperative grid that never calls grid.sync() is held back just the same.

Five stragglers: 143 free SMs is not enough#

Switch the viewer above to 5 stragglers · A cooperative + grid sync · B submitted first. Now 148 − 5 = 143, one SM short. A doesn’t start at 3.1 ms. It starts at 4,600.8 µs, right after the fifth straggler (4.5 ms of work + 0.1 ms tail) ends. When it starts, the other four stragglers are still running, so again exactly 4 B blocks are live. A then uses the fifth straggler’s SM (146) and avoids SMs 142–145. The medians: 4.600 ms with or without the barrier.

This is the cleanest evidence for all-or-nothing admission. The start time is set by the moment the free-SM count reaches 144, not by when “B is done” or “most of B is done”.

Control: an ordinary A starts immediately#

With cudaLaunchKernel there’s no co-residency promise, so the distributor uses whatever is free. A started 57 µs after B in this run (median 17 µs over 20 trials) while all 96 B blocks were still running. It ran in three waves: 52 blocks at once, 51 more between ≈ 2.1 and 2.7 ms on those same SMs as A’s own blocks finished, and the last 41 at ≈ 3.1 ms on SMs that B had freed. The median trial started 103 A blocks before the first B block exited. That count is cumulative across waves, not simultaneous residency.

The ordinary A finished at ≈ 5.2 ms in this run. The cooperative A, which waited, finished at ≈ 6.2 ms (no barrier) or ≈ 6.7 ms (barrier). Gang admission has a cost when the GPU is shared.

Inside the barrier: arrival imbalance, not barrier cost#

The long “grid sync” slices look like an expensive barrier. They aren’t:

  • Block 0 does 1 ms more work by design, so it arrives 1 ms late. Every other block arrives at ≈ 2 ms and waits about 1.0 ms (median max wait 1.0008 ms). Block 0 itself waits ≈ 1 µs.
  • Once block 0 arrives, the release is fast. All 144 blocks left the barrier within 0.13 µs of each other in this run.
  • After the barrier, block 1 spins 0.6 ms instead of 0.1 ms. There’s no second barrier, so nobody waits for it. It only stretches the kernel’s end by 0.5 ms (median exit spread 500 µs), and every other block exits on time.

Before blaming a long sync slice on synchronization overhead, compare arrival times across blocks. The slice length mostly measures how late the slowest block arrived.

A first: the barrier holds SMs hostage#

Flip the order and A gets the GPU first in every configuration (ordinary or cooperative makes no difference when the SMs are empty). B gets only the 4 spare SMs, and its first four blocks, the stragglers, take them. The question is when the other 92 B blocks get in:

  • No grid sync: A blocks exit at ≈ 2.1 ms (block 0 at 3.1 ms), and B’s blocks move in right away. The last regular B block ended at ≈ 5.2 ms.
  • Grid sync: every A block sits at the barrier until block 0 arrives at 3 ms, keeping its SM the whole time. The last regular B block ended at ≈ 6.2 ms.

Those are single profiled runs. The B-last-end numbers are dominated by the 6.1 ms stragglers in both cases, so the repeated-trial spans hide the difference. In the timeline, the extra 1 ms of hatched “waiting” in A is 1 ms that 140-odd SMs could have spent on B.

Companion: Triton, many blocks per SM#

An earlier round of runs tried the same two-stream idea in Triton, before the straggler version existed. Same shape: A is 144 cooperative blocks that spin 2 ms (block 0 spins 3 ms), B is 96 ordinary blocks that spin 3 ms, and every block writes the same five stamps. The kernel, lightly reformatted, with comments added:

@triton.jit
def stamp():                                  # %globaltimer, as in the CUDA version
    return tl.inline_asm_elementwise("mov.u64 $0, %globaltimer;", constraints="=l",
                                     args=[], dtype=tl.uint64, is_pure=False, pack=1)

@triton.jit
def toy(out, counter, count: tl.constexpr, barrier: tl.constexpr, delay: tl.constexpr):
    idx = tl.program_id(0)                    # Triton's name for blockIdx.x
    start = stamp()
    sm = tl.inline_asm_elementwise("mov.u32 $0, %smid;", constraints="=r",
                                   args=[], dtype=tl.uint32, is_pure=False, pack=1)
    while stamp() - start < delay + (idx == 0) * 1000000:   # "work"; block 0 +1 ms
        pass
    arrival = stamp()
    if barrier:                               # hand-rolled grid barrier:
        tl.atomic_add(counter, 1, sem="acq_rel", scope="gpu")           # "I'm here"
        while tl.atomic_add(counter, 0, sem="acquire", scope="gpu") < count:
            pass                                                         # wait for all
    passed = stamp()
    while stamp() - passed < 100000 + (idx == 1) * 500000:  # "tail"; block 1 +0.5 ms
        pass
    tl.store(out + idx * 5, sm)               # one row per block: [sm, t0, t1, t2, t3]
    tl.store(out + idx * 5 + 1, start)
    tl.store(out + idx * 5 + 2, arrival)
    tl.store(out + idx * 5 + 3, passed)
    tl.store(out + idx * 5 + 4, stamp())

Each kernel is launched on its own stream, with A as a cooperative grid:

toy[(count,)](out, counter, count, barrier, delay,
              num_warps=1,                        # 32 threads per block
              launch_cooperative_grid=is_a)       # A: cooperative launch; B: ordinary

Three differences from the CUDA version matter:

  • No shared-memory carveout. Nothing asks for 227 KiB per block, so a block is just one warp of 32 threads with whatever registers Triton chose.
  • The barrier is an atomic counter, not this_grid().sync(). Each block bumps the counter, then spins until it reaches count. This is only safe because of the cooperative launch: if some A block were never admitted, everyone else would spin forever on SMs it needs. The counter is reset between runs.
  • One kernel body for both A and B, so B’s block 0 and block 1 get the same tweaks as A’s, and B has no stragglers.

Why several blocks now fit on one SM. Run the admission check from Part 1 on a Triton block: 32 threads out of 2,048, no shared memory to speak of, one of 32 block slots. Threads alone would allow 64 blocks per SM; the 32-slot limit caps it at 32, unless registers bind first (65,536 ÷ 32 threads ÷ 32 blocks = 64 registers per thread; Triton’s actual register count wasn’t recorded). Either way an SM that already holds a B block has plenty left for an A block. So the free capacity on the GPU at t ≈ 0 isn’t “52 SMs”; it’s room for well over 144 more blocks.

What the trace shows:

  • A started while all 96 B blocks were still running. All 144 A blocks started within 0.6 µs of each other, about 0.12 ms after the first B block. B’s first block exit came at 3.1 ms. The 0.12 ms gap is probably the host-side gap between two Triton launches; it wasn’t measured.
  • 92 SMs held one A block and one B block at the same time. No SM ever held more than two. That’s the tightest possible packing: 144 + 96 = 240 blocks on 148 SMs means at least 240 − 148 = 92 SMs have to double up, and exactly 92 did. Here the distributor spread blocks across SMs instead of stacking them. That’s observed, not documented.
  • This is consistent with gang admission, not a counterexample. The cooperative grid still started all at once. It just didn’t have to wait, because all 144 blocks fit on top of B immediately.

The lesson: “free SM” means free resources, not “an SM with nothing on it”. The carveout in the main experiment is what turned SMs into whole slots and made the waiting visible. This isn’t a matched replication of the straggler experiment: there are no stragglers, and the barrier is different.

Lessons#

  1. Streams give ordering, not capacity. Two “concurrent” streams share one pool of SMs, and whoever holds an SM keeps it until its block exits.
  2. Admission is about whole blocks fitting. Big shared-memory or register footprints turn SMs into coarse slots. That’s what made this experiment readable, and it’s what makes real kernels block each other.
  3. A cooperative launch is gang-scheduled in practice. It waits for room for the entire grid, even with no grid.sync() in the code, and even while many SMs sit idle. If you share a GPU with other streams, size cooperative grids below the SM count you can actually expect to be free.
  4. Kernel-level traces show when, block-level traces show why. The PyTorch trace showed A starting 3.1 ms late. Per-block %smid + %globaltimer stamps showed the four SMs it was waiting on.
  5. Read barrier slices as arrival skew first. A 1 ms sync slice here was one late block, not a slow barrier.
  6. Barriers hold resources. Blocks waiting at a grid barrier are resident and keep their SMs, which delays other streams’ work.
  7. Change one thing at a time, and repeat. Each claim above comes from comparing arms that differ in exactly one flag, with medians of 20 alternating-order trials, not a single trace.

Open questions and next steps#

  • Where is the cooperative grid held? In the driver, the front end or the distributor? Nsight Systems’ GPU trace, or launching from a CUDA graph, might separate those.
  • Unequal stragglers. A variant with three +3 ms stragglers and one +5 ms straggler is written but not run. The prediction: A still starts at ≈ 3.1 ms, because that’s when the free-SM count reaches 144, however long the four stragglers keep running after that.
  • Priorities. Does a high-priority stream let an ordinary grid jump ahead of a waiting cooperative grid on newly freed SMs?

Reproducing it#

On any idle GPU with 148 SMs and sm_100 (other SM counts need the block counts adjusted), check nvidia-smi first. Then run one arm per configuration:

DEMO=cuda OUT="$PWD/out" COOP=1 BARRIER=1 STRAGGLERS=4 python3 demo.py   # coop + grid sync
DEMO=cuda OUT="$PWD/out" COOP=1 BARRIER=0 STRAGGLERS=4 python3 demo.py   # coop, no sync
DEMO=cuda OUT="$PWD/out" COOP=0 BARRIER=0 STRAGGLERS=4 python3 demo.py   # ordinary

Each run writes the PyTorch trace, the per-block tensors for both launch orders, and the 20-trial summary.
