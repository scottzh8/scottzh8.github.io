Learning notes · GPU kernels · Study 2 · Nov 2026

Question: when you replace a chain of kernel launches with a CUDA graph, what exactly gets faster: the CPU, the GPU, or both? And why?
Hardware: NVIDIA B200, 148 SMs, sm_100 (two physical GPUs over the study)
Tools: CUDA C++ (nvcc -O2 -arch=sm_100), per-block %globaltimer / %smid stamps, std::chrono on the host, the occupancy API
Status: study notes. Every number below is a median of repeated runs unless marked as a single measurement. Observed behavior on this device and driver, not a guarantee about every CUDA device.

TL;DR

  • A graph saves GPU time, not just CPU time. With the CPU far ahead, the idle gap between two kernels was 1,024 ns eager vs 768 ns in a graph (medians), at every kernel length from 0.5 to 50 µs. That’s ~0.28 µs per kernel boundary: 275 µs per 1,000 kernels.
  • Below ~0.5 µs of kernel time, eager launches are CPU-bound. Each launch call costs ~1.5 µs of CPU; the GPU waits for it. There a graph cut wall time by 44–47%.
  • Launch data lives in different places. Eager launches write their commands and arguments into a write-combined host-RAM buffer, ~2.4 KB per launch. A graph’s launch data takes GPU memory at instantiate; replays don’t re-read arguments from host RAM. Argument size (24 B to 32 KB) doesn’t change either gap.
  • Programmatic dependent launch (PDL) removes another 256 ns step, and it stacks with graphs: graph + PDL gaps were 512 ns, half of plain eager.
  • A graph freezes every argument, pointers included. Patching 1,000 nodes in place (cudaGraphExecKernelNodeSetParams) cost ~0.34 ms in total vs ~5 ms to rebuild.
  • Side quest: the chip’s map. Block placement is deterministic. Thread-block clusters reveal 8 GPCs (10, 4×18, 3×20 SMs) plus three standalone SM pairs, and the GPC shape caps how much of the GPU a cluster size can use: size 2 → 100%, 4 → 89%, 8 → 81%, 16 → 76%.

The route#

Study 1 followed one launch from a CUDA stream down to an SM. It left one number unexplained: the time between kernels. Real workloads launch thousands of short kernels, CUDA graphs are the standard fix for launch overhead, and I wanted to know what that fix actually removes.

The map at the top shows the whole machine and the road every launch takes to the GPU. Each stop below zooms into one part of it.

The plan had five stops. Each one either builds an instrument or uses one:

The method at every stop was the same: write a prediction down, run, compare. I got several of them wrong, and I’ve left those in, since each wrong prediction is what led to the next experiment.

Stop 1: calibrating the stopwatch#

The spin kernel#

Every experiment uses one deliberately boring kernel. Each block spins for exactly D nanoseconds on the GPU’s global timer, then thread 0 writes when it started and ended:

__device__ unsigned long long globaltimer() {
    unsigned long long t; asm volatile("mov.u64 %0, %%globaltimer;" : "=l"(t)); return t;
}
__global__ void spin(unsigned long long *out, unsigned long long D_ns) {
    unsigned long long start = globaltimer();
    while (globaltimer() - start < D_ns) { }
    unsigned long long end = globaltimer();
    if (threadIdx.x == 0) { out[2 * blockIdx.x] = start; out[2 * blockIdx.x + 1] = end; }
}

148 blocks of 32 threads, and one trick: request the maximum opt-in dynamic shared memory per block (232,448 B on this GPU). Then only one block fits per SM, so 148 blocks means exactly one block on each SM.

int smem = 0;
cudaDeviceGetAttribute(&smem, cudaDevAttrMaxSharedMemoryPerBlockOptin, 0);
cudaFuncSetAttribute(spin, cudaFuncAttributeMaxDynamicSharedMemorySize, smem);
spin<<<148, 32, smem, stream>>>(d_out, D);

Is the stopwatch fine enough?#

Background: which clock? A kernel can read two different clocks, and they answer different questions. This part is from NVIDIA’s docs, not from my measurements:

  • clock64() (PTX %clock64) counts SM clock cycles. The PTX ISA calls it a 64-bit “cycle counter”; the CUDA C++ Programming Guide is more specific: a per-multiprocessor counter incremented every clock cycle. So its rate follows the SM clock, which isn’t fixed (Stop 3’s clock log saw 975, 1,290 and 1,965 MHz), and each SM has its own counter. The docs don’t say the counters on different SMs agree.
  • %globaltimer is, in the PTX ISA’s words, “a predefined, 64-bit global nanosecond timer”. Its unit is real time, whatever the SM clock is doing, and it is global, so a stamp taken on one SM can be compared with a stamp taken on another. A gap needs exactly that: the last block of kernel k and the first block of kernel k+1 usually run on different SMs. That’s why the spin kernel uses it. The same entry also warns that these registers are meant for NVIDIA’s tools and that their behavior is target-specific.

Why measure it? The docs give the unit (nanoseconds) but not how often the value actually changes, and they say the behavior depends on the GPU. My worry going in was that it might change only about once a microsecond. That’s the same size as the gaps I wanted to measure: every gap would read as 0 or 1 µs, and a difference of a few hundred nanoseconds between eager and graph would be invisible. So the first experiment asks one question: how big is one tick of %globaltimer on this B200?

It’s a separate, tiny program, not the spin kernel: a single GPU thread (tick<<<1, 1>>>) reads the timer in a tight loop. Each time the value changes, it records how far the value jumped and how many reads it took to see the change:

__global__ void tick(unsigned long long *jump_ns, unsigned *reads, int n) {
    unsigned long long prev = globaltimer();
    for (int i = 0; i < n; i++) {
        unsigned long long t; unsigned same = 0;
        // spin until the value moves, counting reads
        do { t = globaltimer(); same++; } while (t == prev);
        jump_ns[i] = t - prev;   // how far it moved
        reads[i]   = same;       // 1 = the first read already saw it move
        prev = t;
    }
}

It ran until it had recorded 20,000 changes.

Result 1: one tick is 32 ns. Every jump was a multiple of 32 ns: 8,782 jumps of 32 ns, 11,217 of 64 ns and one stray 256 ns. If the value changed every nanosecond, the jumps would be all sorts of sizes; if it changed every 16 ns, some jumps would be 48 ns. In 20,000 jumps there was nothing but multiples of 32.

Result 2: the loop is slower than the tick. The read count was 1 every time: the very first read after a change already returned a new value. If one trip around the loop took less than 32 ns, the loop would sometimes read the same value twice before it changed (left panel below). That never happened. And apart from the one stray, no jump was 96 ns or more, so no trip took that long either. Each trip took between one and two ticks:

Since every trip saw a change, the jumps add up to the total time, so the average jump is the average trip: about 50 ns. Is that expected? I didn’t have a prediction. It does say that reading %globaltimer is not free: one trip (a read, a compare and a branch) costs roughly 100 SM cycles. I didn’t break that down further.

So the answer to “how fine is the stopwatch?” is: a stamp is good to about 32–64 ns, one tick plus the cost of taking it.

In GHz terms. One update every 32 ns is 31.25 million updates per second, so the timer behaves like a 31.25 MHz clock. The SM clock is much faster: during the overhead sweep in Stop 3 (a later run, where I logged it) it sat at 1,965 MHz, about 0.51 ns per cycle. Putting the scales side by side:

So the timer is coarse next to the SM clock: one tick lasts about 63 SM cycles. But the gaps this post is about are dozens of ticks long, and the difference between eager and graph is 8 ticks. Microsecond gaps are directly measurable, and the worry about a once-a-microsecond timer doesn’t apply on this GPU.

One kernel, 148 blocks#

With D = 10 µs: 148 distinct SM IDs, every block ran 10,016–10,048 ns, and all 148 blocks took their first timer read within 0–64 ns of each other. No block-by-block dispatch delay is visible at this scale. A kernel’s span is D plus roughly 50–100 ns.

That gives the measurement for the rest of the post:

One rule I kept throughout: CPU and GPU clocks are never subtracted from each other. CPU-side times (launch calls, wall time) come from std::chrono::steady_clock (a pair of reads costs 15 ns). GPU-side times (spans, gaps) come only from the stamps.

Stop 2: mapping the chip#

This stop was meant to be a quick sanity check, and it turned into a detour. It’s worth taking, because the map it produces explains a real limit on how you size thread-block clusters.

Where does block 0 go?#

Finding: for a given grid size, block placement is fully deterministic, and a partial grid is spread evenly across the GPCs (graphics processing clusters, the hardware unit above the SM). After the three standalone SM pairs (142–147), each round takes one SM pair from every GPC, until the small GPC A runs out. Every grid size from 1 to 148 blocks, launched 10 times each in two processes (2,960 launches), gave exactly the same placement.

Two things to notice:

  • SMs fill in ID order: 142–147 first, then 0–15, 16–31, and so on. A row of IDs fills before the next one starts.
  • Which block index lands where depends on the grid size. Block 8 runs on SM 2 in a 16-block launch but on SM 16 in a 25-block launch. Nothing moved between them; indices are dealt out GPC by GPC, which the GPC map below explains.

The GPC part took a detour to see. Without a GPC map, those rows of IDs were all I had, and the obvious guess was that each row is a GPC.

Testing the guess with clusters#

The guess: each row of SM IDs in the placement figure is one GPC. That would make five GPCs of 16 SMs (0–15 … 64–79), four of 14 (80–93 … 122–135) and two groups of 6 (136–141, 142–147).

The test: thread-block clusters. A cluster is a group of blocks that CUDA guarantees to run inside one GPC. With one block per SM, a cluster of k blocks needs k free SMs in a single GPC. So the GPC sizes decide how many k-clusters fit on the chip at once. CUDA will report that number without launching anything. The code describes one cluster of k blocks and asks:

// 1. Clusters over 8 blocks are "non-portable"; opt in so k can go up to 16.
cudaFuncSetAttribute(cspin, cudaFuncAttributeNonPortableClusterSizeAllowed, 1);

// 2. A launch attribute that says "group the blocks into clusters of k".
cudaLaunchAttribute attr;
attr.id = cudaLaunchAttributeClusterDimension;
attr.val.clusterDim.x = k;  attr.val.clusterDim.y = 1;  attr.val.clusterDim.z = 1;

// 3. The launch shape: k blocks (one cluster), 32 threads each, and the maximum
//    shared memory per block, so only one block fits on an SM.
cudaLaunchConfig_t cfg = {};
cfg.gridDim = dim3(k);  cfg.blockDim = dim3(32);  cfg.dynamicSmemBytes = smem;
cfg.attrs = &attr;  cfg.numAttrs = 1;

// 4. Ask: how many clusters of this shape can run on the GPU at the same time?
int fit = 0;
cudaOccupancyMaxActiveClusters(&fit, cspin, &cfg);

The prediction, if rows are GPCs: a 16-cluster fits once in each 16-SM row and nowhere else, so 5 fit. The same counting gives the middle row of this table (for k = 12: 9, or 10 if 136–147 act as one 12-SM group). The measurement is the bottom row:

Every prediction was wrong, so rows are not GPCs. To make sure the API wasn’t misleading me, I also launched exactly fit clusters (all started together) and then fit + 1 (exactly k blocks started late), for every k. The largest cluster allowed was 16.

The real map#

The same clusters reveal the true map. Blocks of one cluster always share a GPC, so any SMs that ever ran in the same cluster are in the same GPC. Each block recorded its SM (%smid) and cluster (%clusterid), and grouping SMs this way over all 1,080 clusters launched gives 11 groups:

This map predicts every measured count. For k = 10: A fits 1, B–E fit 1 each, F–H fit 2 each → 11.

Now press Show GPCs on the placement figure. Each row of IDs is really a slice across the GPCs: one SM pair (a TPC, the two-SM unit) from each GPC. That is the payoff of this detour:

SM IDs interleave the GPCs, so filling SMs in ID order spreads a partial grid evenly across the GPCs.

The map also explains the reshuffled block indices: indices are dealt GPC by GPC. At 25 blocks GPC A has two pairs in use and takes blocks 6–9; at 16 blocks it has one pair and takes 6–7, so block 8 goes to GPC B’s SM 2.

A later run landed on a second, physically different B200. Its map was identical, SM for SM. I don’t know whether that’s coincidence or a standardized logical numbering.

Clusters and idle SMs#

With the map, idle SMs become predictable: in each GPC, whatever is left over after packing whole clusters sits idle, and free SMs scattered across GPCs can’t host a cluster. That’s fragmentation. I wrote predictions for the second GPU from the map before running:

All confirmed, including which SMs sit idle: inside each GPC, the highest-ID pairs. Pick a cluster size and see for yourself:

Takeaway for kernel design. A cluster must fit inside one GPC, so the GPC shape caps the SMs a cluster size can use (one block per SM, worst case): size 2 → 100%, 4 → 89%, 8 → 81%, 16 → 76%. Every GPC and standalone pair has an even SM count, so size 2 always uses all 148. Default to no cluster or size 2, and go bigger only when the cooperation gain beats that ceiling. Read the ceiling at runtime with cudaOccupancyMaxActiveClusters instead of hard-coding a map; other chips may differ, and with several blocks per SM the arithmetic changes.

Stop 3: eager vs graph, where’s the saving?#

Back to the main question, with a stopwatch I trust.

What a graph is#

From the CUDA programming guide: a CUDA graph is a recorded set of operations and their dependencies, defined once and launched many times. You can build one by capturing a stream: launches between cudaStreamBeginCapture and cudaStreamEndCapture are recorded instead of run. Instantiate turns the graph into an executable graph, with most setup done once; upload moves it to the device ahead of the first launch (otherwise the first launch does it); a replay launches the whole thing with one call.

// eager: N launch calls
for (int k = 0; k < N; k++)
    spin<<<148, 32, smem, stream>>>(d_out + k * 148 * 2, D);

// graph: record the same loop once…
cudaGraph_t graph; cudaGraphExec_t exec;
cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
for (int k = 0; k < N; k++)
    spin<<<148, 32, smem, stream>>>(d_out + k * 148 * 2, D);
cudaStreamEndCapture(stream, &graph);
cudaGraphInstantiate(&exec, graph, 0);
cudaGraphUpload(exec, stream);

// …then replay it with one call
cudaGraphLaunch(exec, stream);

First contact: 10 kernels#

Prediction: at D = 2 µs, an eager launch call takes longer than a kernel, so the GPU starves and the graph wins big. At D = 1 ms the CPU is far ahead and (if H1 holds) the two match.

Per chain of 10 kernels; 20 repetitions per arm, medians. Each kernel’s span was 2.08 µs at D = 2 µs. Wall saved = eager wall time − graph wall time, as a share of eager.

  • The CPU saving is real: 10 kernels cost 18.2 µs of launch calls eager, 1.75 µs as one replay (about one eager launch), so 90% less CPU time. The CPU’s own thread time matched the elapsed time inside the calls: a launch call is busy CPU work, not waiting.
  • My starvation prediction was wrong. An eager call took ~1.8 µs, just under the 2.08 µs kernel, so the CPU kept up, and the gaps were the same at 2 µs and 1 ms.
  • And yet the graph’s gaps were shorter, 0.77 vs 1.02 µs, at both lengths. That’s H2’s signature.
  • Read the percentages with care. The graph saved about the same ~3 µs of wall time at both lengths. That’s 7% of a chain of 2 µs kernels but 0.03% of a chain of 1 ms kernels. The saving is per kernel boundary, so it matters when kernels are short.

Longer chains#

Next I scaled N from 10 to 10,000 at D = 2 µs and 50 µs. For N ≥ 100 the graph won by a fixed amount per kernel, about the same at both kernel lengths, so the absolute saving grew linearly with N (48 µs at 100, 0.48 ms at 1,000, 6.9 ms at 10,000) while the relative saving shrank with D (13–19% at 2 µs, ~1% at 50 µs). Two things in this run didn’t hold up later, though: at N = 10 the gap difference disappeared, and the eager gaps for N ≥ 100 came out at 1.5 µs, a value the next run never saw again.

Two observations from it did hold:

  • The eager launch queue fills. With 10,000 launches of 50 µs kernels, the median launch call took 51.2 µs, and 89% of calls took over 10 µs. Once the queue is full, each call waits for the GPU to finish a kernel: the CPU thread was blocked for 462 ms of the 515 ms run. The graph issued the same work in one call.
  • A replay call grows with N: 1.7 µs (10 kernels), 1.9 µs (100), 5.7 µs (1,000), 30–89 µs (10,000). Still far below eager issue.

The clean sweep#

To settle the size of the effect, I ran one sweep with eager and graph interleaved (alternating order every repetition) and the SM clock logged throughout (1,965 MHz in 32 of 38 samples; the rest at the edges of the run). Kernel length went from D = 0 (an empty spin: 0.26 µs span) to 50 µs, at N = 10, 100 and 1,000, with 10 repetitions each.

What the sweep shows:

  1. A graph makes every handoff one 256 ns step shorter: 1,024 ns eager vs 768 ns graph, for every kernel length from 0.5 to 50 µs. That’s ~0.28 µs per kernel, or ~275 µs per 1,000 kernels.
  2. Below ~0.5 µs kernels, eager launching is the bottleneck. Each launch call takes ~1.5 µs of CPU, longer than a short kernel plus its gap, so the GPU sits waiting for the CPU. A graph removes that wait too and cuts wall time by 44–47%.
  3. Longer kernels shrink the payoff. The saving per handoff stays the same, so its share of wall time falls: 17% at 0.5 µs kernels, 9% at 2 µs, 2.5% at 10 µs, 0.5% at 50 µs.

This interleaved sweep supersedes the ~0.48 µs per kernel from the longer-chain run above, whose eager gaps were an unusually long 1.5 µs.

Finding

H2 holds. A graph also makes the GPU’s kernel-to-kernel changeover cheaper: by one 256 ns step in the clean sweep, and by one to three steps across all runs.

Which raises the next question: why?

Stop 4: why are graph gaps shorter?#

I had three suspects:

  • H-fetch: eager launch data (commands, kernel arguments) sits in host RAM, and the GPU fetches it over PCIe at each kernel boundary, while a graph’s data was pre-uploaded to GPU memory.
  • H-sync: eager streams do per-kernel completion bookkeeping that a graph only does at the end.
  • H-prefetch: a graph knows its whole dependency chain in advance, so the GPU can stage the next launch before the current kernel ends.

H-fetch makes a testable claim about where launch data lives, so I started there.

Where does launch data live?#

The test: launch a kernel whose argument is a distinctive marker value, then search the process’s own driver memory mappings (the /dev/nvidia* lines in /proc/self/maps) for it. To classify the memory a marker turns up in, I timed CPU reads against reference buffers whose location is known:

Eager: right after four marked launches returned (before any sync), the four markers sat in a 64 MiB /dev/nvidiactl mapping that reads at 121 ns per load, i.e. write-combined host RAM. They were 2,432 bytes apart, one per launch, with the grid size (0x94 = 148) among the surrounding words and the kernel’s other argument right after the marker. The kernel arguments are written inline into a command stream in host RAM, and the GPU has to pull them from there over PCIe.

What does “write-combined” mean? It’s a memory type built for memory the CPU writes and a device reads:

That trade fits a command buffer exactly. The CPU writes each launch once and never reads it back; the GPU reads it. The one downside, slow CPU reads, doesn’t matter there, and it’s the 121 ns signature that identified the buffer.

Who sets it: the driver, when it maps the buffer into the process. On Linux, drivers request it through standard kernel helpers (for example pgprot_writecombine), and the CPU’s page tables enforce it. cudaHostAllocWriteCombined asks for the same for your own buffers. I identified the type by read cost; I didn’t read the page attributes.

Graph: no marker anywhere after capture or instantiate. After cudaGraphUpload, the four markers appeared once in the same host buffer, and replays wrote no new copies. Then the decisive test: after upload, 100,000 other eager launches overwrote that host buffer completely (graph marker hits → 0). The replay still used the right arguments. So a replay doesn’t read its arguments from host RAM. Upload passes them through once, to somewhere the GPU keeps them. Stop 5 shows the graph taking GPU memory at instantiate, in proportion to its argument bytes, which makes GPU memory the likely place. I haven’t proven it.

Suspect 1 cleared: argument bytes don’t matter#

If eager gaps are longer because argument bytes cross PCIe inside the gap, then bigger arguments should mean longer eager gaps. I padded the kernel’s arguments from 24 B up to 32,000 B (with D = 50 µs, so the CPU is far ahead):

Kernel arguments24 B1 KB4 KB16 KB32,000 B
eager gap, median / mean (ns)1,024 / 1,0521,024 / 1,0521,024 / 1,0491,024 / 1,0531,024 / 1,052

Flat. Pulling 32 KB across PCIe in the gap would have shown up, so the GPU front end must read eager command data ahead, while the previous kernel still runs. H-fetch in its simple form is rejected: host RAM alone doesn’t explain the graph’s advantage. The gaps were also the same at every position in the chain (k = 0 to 998) and at N = 10, 100 and 1,000.

Overlapping launch work: programmatic dependent launch#

If the gap isn’t data transfer, maybe part of it is launch processing for the next kernel. Programmatic dependent launch (PDL) is the documented way to let that overlap. Per the CUDA programming guide:

  • The host sets a launch attribute on the second kernel’s launch: cudaLaunchAttributeProgrammaticStreamSerialization. That allows it to begin launching before the first kernel has finished.
  • The first kernel signals when its dependents may launch (cudaTriggerProgrammaticLaunchCompletion(), PTX griddepcontrol.launch_dependents). If it never triggers, the trigger happens when it completes.
  • The second kernel calls cudaGridDependencySynchronize() (PTX griddepcontrol.wait) before it touches anything the first kernel wrote. That call waits for the first grid to complete and its memory to be visible.

The safety rule is that last bullet: anything before the wait may run while the previous kernel is still running. In my chain every kernel is both a “second” and a “first”, so it triggers immediately and then waits before stamping its start time:

__global__ void spin_pdl(unsigned long long *out, unsigned long long D_ns) {
    asm volatile("griddepcontrol.launch_dependents;");   // let the next kernel start launching
    asm volatile("griddepcontrol.wait;" ::: "memory");   // wait for the previous kernel
    unsigned long long start = globaltimer();
    while (globaltimer() - start < D_ns) { }
    /* stamp start/end as before */
}

cudaLaunchAttribute attr;
attr.id = cudaLaunchAttributeProgrammaticStreamSerialization;
attr.val.programmaticStreamSerializationAllowed = 1;
cfg.attrs = &attr; cfg.numAttrs = 1;
cudaLaunchKernelEx(&cfg, spin_pdl, out_k, D);

Finding

  • It isn’t data transfer. Eager arguments do live in host RAM, but the gap didn’t change from 24 B to 32,000 B of arguments.
  • A graph alone saves as much as PDL. With no code changes, a graph shortens each gap by one 256 ns step (1,024 → 768 ns), the same step PDL removes from eager launches. Together they save two steps (1,024 → 512 ns). PDL was measured with 50 µs kernels only.
  • How a graph replay saves that step is unknown. Skipped per-kernel bookkeeping (H-sync) and staging the next launch early (H-prefetch) are both still candidates; I didn’t test them. If you know, I’d love to hear.

Side discovery: the eager queue has a size#

The padded-argument runs turned up something else. With big arguments, the eager launch queue filled before N = 1,000, and launch calls started blocking for a whole kernel (~51 µs):

Subtracting the kernels the GPU finished in the meantime, about 4.4–4.7 MB of launch data (arguments plus ~2.4 KB per launch) was in flight each time a call first blocked. The earlier 16-byte run at N = 10,000 blocked after ~1,030 launches in flight. My inference: the eager queue is limited both by bytes (~4.5 MB) and by entries (~1,024).

Stop 5: the price of a frozen graph#

A graph isn’t free. It has to be built and warmed up, its arguments are frozen, and it owns memory.

One-time costs and warm-up#

  • Setup grows with the number of kernels in the graph. Capture records every launch as a node, and instantiate builds launch data for every node, so both take longer as the chain gets longer: a 10,000-kernel graph took ~20 ms to capture, instantiate and upload, even when warm. The very first graph in a process is much slower still. With 10 kernels, instantiate took 143 µs the first time and 12–20 µs after that.
  • The first replay is slow even after an explicit upload. Upload should have done the one-time work, yet the first replay call was always the slowest, and things settled by about the third replay. With 10 kernels the call took ~3 µs the first time vs ~1.5 µs once warm; with 10,000 kernels, 29 µs vs 10 µs. Why is still an open question.
  • Setup pays for itself within a handful of replays. For chains of 100 kernels or more, the setup cost equals the wall time a graph saves in roughly 5 replays (more for the first graph in a process). A real serving or training job replays the same graph far more often than that, typically once per step, so the setup cost disappears quickly.

Frozen arguments, and three ways to change them#

A graph freezes every launch’s arguments, including pointers: replays always write to the buffers that were captured. To point a 1,000-kernel chain at a new output buffer, I tried each option (single measurements, each correctness-checked):

NodesReplayPatch every node in place (cudaGraphExecKernelNodeSetParams)Re-capture + cudaGraphExecUpdateFull rebuild (capture + instantiate + upload)
1016.0 µs6.9 µs5.6 + 4.8 µs39.8 µs

Patching in place costs ~0.28 µs per node, 6× (N = 10) to 17× (N = 1,000) cheaper than a rebuild:

size_t n = 0;
cudaGraphGetNodes(graph, nullptr, &n);
std::vector<cudaGraphNode_t> nodes(n);
cudaGraphGetNodes(graph, nodes.data(), &n);
for (auto node : nodes) {
    cudaKernelNodeParams p;
    cudaGraphKernelNodeGetParams(node, &p);          // params as captured
    int k = *(int *)p.kernelParams[1];
    void *args[2] = {&new_out, &k};                  // swap only the output pointer
    p.kernelParams = args; p.extra = nullptr;
    cudaGraphExecKernelNodeSetParams(exec, node, &p);
}

The third option is indirection: the kernel reads its output pointer from a device-memory slot, so redirecting is one 8-byte copy. But every kernel pays an extra dependent load, and replays were ~15–19% slower here (104 vs 90 µs at N = 100; 1,002 vs 843 µs at N = 1,000).

Updates are applied lazily. After patching all 1,000 nodes, the next replay call took 58.9 µs instead of 2.5 µs; after re-capture + update, 41.8 µs. A rebuild without an explicit upload paid ~278 µs at its first replay, which is the upload. So redirecting 1,000 nodes in place costs ~0.34 ms all-in, vs ~5 ms to rebuild.

The memory a graph owns#

Graphs own two kinds of memory, and both are HBM on the GPU, not host RAM: buffers allocated inside the graph with cudaMallocAsync, and the graph’s own launch data. Step through both:

  • Allocations inside a graph take HBM at upload, not at capture or instantiate, and a second identical graph on the same stream reused the same 1 GiB. Destroying both didn’t release it; cudaDeviceGraphMemTrim did.
  • The graph itself takes HBM at instantiate: ~2.2 KB per node with tiny arguments, plus the arguments themselves (32 KB × 1,000 nodes: +30 MiB on top). Upload copies the data in (~0.33 ms for 1,000 nodes) without taking more. This is the evidence behind the “inferred” arrow in the launch-path figure.

Lessons#

  1. Ask which overhead. “Graphs reduce launch overhead” hides two separate savings: CPU launch calls (big, but only matters when the CPU is the bottleneck) and GPU handoff (small, ~0.28 µs per boundary, but always there).
  2. The crossover is set by kernel length. Here it was at ~0.5 µs. Below it, eager launches starve the GPU and graphs nearly halve wall time; above it, the saving is ~0.28 µs × (N − 1).
  3. Calibrate before you measure. Checking the timer’s tick and running a one-kernel sanity check first made every later gap number trustworthy, down to the 256 ns steps.
  4. Write predictions down. My predictions for GPU starvation, the GPC map and cluster counts were all wrong, and every miss pointed at the next experiment.
  5. Interleave the arms. An early run’s eager gaps (1.5 µs) never reproduced. The interleaved sweep with a clock log is the one I trust.
  6. Clusters have a hidden cost. GPC shape caps usable SMs; ask the occupancy API rather than assume.
  7. A graph is a frozen snapshot that owns memory. Plan for pointer changes (patch in place, or indirection) and for graph memory that stays reserved until you trim it.

Open questions#

  • Why is every gap a multiple of 256 ns, when the timer ticks at 32 ns?
  • Why do absolute gap values shift by 256–512 ns between programs and runs (eager 1.5 µs in one run, 1.0 µs in the next, for a similar setup), while graph ≤ eager always holds?
  • Why is the first replay slower even after an explicit upload?
  • Which mechanism removes the graph’s piece of the gap: skipped per-kernel completion bookkeeping, or staging the next launch early?
  • In the sweep at D = 0, N = 1,000, the graph’s wall time (889 µs) is below 999 gaps × 0.77 µs plus 1,000 spans × 0.26 µs (~1,031 µs). Spans weren’t saved per arm, so the graph’s own spans there need a recheck.
  • After patching a graph to a new buffer, replays took 665 µs instead of 843 µs. One measurement, unexplained.
  • Why do SMs 142–147 fill first, and is the identical map on two GPUs a standardized numbering?

Reproducing it#

Every experiment is a single CUDA C++ file, compiled and run the same way:

nvcc -O2 -arch=sm_100 chain.cu -o chain && ./chain

The pieces you need are the snippets above: the spin kernel, the one-block-per-SM shared-memory request, per-block stamps read back with cudaMemcpy, gaps computed as in the stopwatch figure, and host timing with std::chrono::steady_clock around each call. On a GPU with a different SM count, change the 148.
